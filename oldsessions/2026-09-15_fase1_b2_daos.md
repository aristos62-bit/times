# Φάση 1 — Βήμα 2: DAOs με CRUD + streams

> Ημερομηνία: 15-09-2026 · Αναφορά: DESIGN §3 (σχήμα), §4.1 (Βήμα 2), app_exceptions.dart (σύμβαση exceptions)

## Τι υλοποιήθηκε

- **`lib/data/local/base_dao.dart`** — SPoT βάση όλων των DAO (κράτα τη σύνδεση `AppDatabase` + guards):
  - `guard(action, op)`: εκτελεί async op, σε σφάλμα λογκάρει (tag `DB`, AppLogger §1.7) και **rethrow raw**.
  - `guardStream(action, builder)`: ίδια λογική σε streams (watch) — κατασκευή και κάθε σφάλμα.
  - **Συμμετρικό error-handling**: read/watch/write συμπεριφέρονται ΟΜΟΙΑ (log + raw rethrow)· το mapping σε `AppException` (π.χ. `DataLoadException`) είναι αποκλειστικό δικαίωμα του Repository (Φάση 2) — σύμβαση του docstring του app_exceptions.dart. Κανένα exception δεν «μασκαρεύεται» στο data layer.
  - Δεν χρησιμοποιείται `@DriftAccessor` ούτε το generated `db.managers` API (καθαρά ονομασμένα contract με ελληνικά ονόματα μεθόδων, όχι αυθαίρετο manager API).
- **7 DAOs σε `lib/data/local/daos/`** (ένα ανά πίνακα, <500 γρ. το καθένα):
  | DAO | Βασικές μέθοδοι |
  |---|---|
  | `CategoryDao` | `watchAll()` (order name) · `getById` · `insert(name)` · `updateById` · `deleteById` |
  | `SubCategoryDao` | `watchAll()` (order name) · `watchByCategoryId` · `getById` · `insert(categoryId, name)` · `updateById` · `deleteById` |
  | `UnitDao` | `watchAll()` (order name) · `getById` · `insert(name, abbreviation, [allowsDecimal])` · `updateById` · `deleteById` |
  | `ItemDao` | `watchAll()` (order normalizedName) · `watchBySubCategoryId` · `getById` · `getByNormalizedName` · `insert(subCategoryId, name, [defaultUnitId])` · `updateById` · `deleteById` |
  | `SupplierDao` | `watchAll()` (order normalizedName) · `getById` · `getByNormalizedName` · `insert(name)` · `updateById` · `deleteById` |
  | `ReceiptDao` | `watchAll()` (order date desc, id desc) · `getById` · `insert(date, supplierId)` · `updateById` · `deleteById` |
  | `ReceiptLineDao` | `watchByReceiptId` (order id) · `getById` · `insert(receiptId, itemId, unitId, quantity, priceCents)` · `updateById` · `deleteById` |

## Αποφάσεις που λήφθηκαν

- **Ονομασμένα params, ΟΧΙ Companion στα public API**: ο caller δεν βλέπει ποτέ `Value`/`Companion`. Τα companions κατασκευάζονται εσωτερικά — είναι λεπτομέρεια του data layer. Κανένα derived field δεν περνάει από τον caller.
- **SPoT υπολογισμένα πεδία μέσα στα DAO (§3)**:
  - `Item.normalizedName` / `Supplier.normalizedName` = `GreekTextNormalizer.normalize(name)` — πάντα εσωτερικά· στον `updateById` ξανα-υπολογίζονται μόλις αλλάξει το `name`.
  - `ReceiptLine.lineTotalCents` = `(priceCents * quantity).round()` — πάντα εσωτερικά· στον `updateById` ξανα-υπολογίζεται όταν αλλάζει quantity ή priceCents (το πεδίο που λείπει διαβάζεται από τη γραμμή).
- **`getByNormalizedName(String)` εξαρχής** σε Item + Supplier — υποστήριξη duplicate-check (§2.2 exact-match) για το seed (Βήμα 3) και τη ροή εισαγωγής (Φάση 3).
- **Ordering** (watch): Κατηγορίες/Υποκατηγορίες/Μονάδες κατά `name`· Είδη/Προμηθευτές κατά `normalizedName` (σταθερή σειρά case/tone-free)· Αποδείξεις κατά `date desc, id desc`· Γραμμές κατά `id`.
- **Validation ΔΕΝ μπαίνει στα DAO** (απόφαση): length/trim/empty/positive checks είναι ευθύνη των validators (Φάση 3) — τα DAO παραμένουν «κουτά» data layer (§2.5). Τα errors τους βγαίνουν απευθείας από τη βάση (UNIQUE/FK) σε raw μορφή.
- **`open()`/`close()`** μένουν στο `AppDatabase` (lifecycle) — τα DAO δεν κάνουν open.
- Μηδέν νέες dependencies: για τα FK tests χρησιμοποιείται το `SqliteException` που re-exportάρεται ΉΔΗ από το `package:drift/native.dart`.

## Debug που βρήκαμε (τεστ, όχι κώδικας)

- Ενώ όλα ήταν πράσινα, τα αρχικά δείγματα των DAO tests ζητούσαν `ρ µα ρκος` με τελικό **ς** (U+03C2). Το `GreekTextNormalizer.normalize('Μάρκος')` επιστρέφει **«μαρκοσ» με τελικό σ (U+03C3)** — ς→σ αφαιρείται. Ο κώδικας ήταν σωστός από πριν (16/16 tests του normalizer το επιβεβαιώνουν)· οι αναμενόμενες τιμές στα νέα tests γράφτηκαν με τον προεπιλεγμένο «ς» του πληκτρολογίου. Διορθώθηκε με ρητό escape `\u03C3` + σχόλιο (SPoT §3).
